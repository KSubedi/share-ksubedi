Graph Database Memory Enhancement

Proposal for TurnPanel's Long-Term Memory Architecture
Executive Summary: This proposal outlines a hybrid vector + graph database architecture to transform TurnPanel's memory system from flat storage into a relationship-aware knowledge graph. Expected outcomes include 10-50x faster relationship queries, 30-50% reduction in token usage, and 90-95% recall accuracy (up from 75-85%).

Current Architecture Analysis

Core Memory (core.json)

  • Structure: Flat JSON array with max 24 entries
  • Storage: Simple key-value facts without relationships
  • Query method: Linear scan or basic filtering
  • Limitation: No awareness of how facts connect to each other

Episodic Memory (vector-db/memories.json)

  • Structure: HNSW vector database with bge-small-en-v1.5 embeddings
  • Capacity: Maximum 5,000 entries
  • Query method: Cosine similarity search (threshold 0.5-0.9)
  • Limitation: Semantic similarity without entity resolution or relationship tracking
Key Gap: Current system cannot answer questions like "What projects does the user work on?" or "What tools does the user prefer for coding?" without scanning all memories and inferring relationships at query time.

Proposed Hybrid Architecture

Core Components

  1. Vector Database (unchanged): Continue using HNSW for semantic similarity search
  2. Graph Database (new): Neo4j or FalkorDB for relationship-aware storage
  3. Entity Extraction Layer: NLP pipeline to identify entities and relationships from raw memories
  4. Hybrid Query Engine: Combine vector search with graph traversal for comprehensive results

Graph Schema Design

Node Labels

Label Example Properties Description
Person {name, email, role} People in user's life (Dana, Ashish, etc.)
Project {name, status, repository} Active development projects (TurnPanel, ALEX, Law Nepal)
Tool {name, category, version} Software tools and libraries (llama.cpp, Composio, tmux)
Preference {type, value, context} User preferences (local-first, WebP, metric units)
Memory {text, timestamp, embedding} Raw memory entries linked to entities

Edge Types

Edge Type Example Properties
USES (User)-[:USES]->(llama.cpp) {since, frequency}
PREFERS (User)-[:PREFERS]->(local-first) {strength, context}
WORKS_ON (User)-[:WORKS_ON]->(TurnPanel) {role, start_date, priority}
MENTIONED_IN (Dana)-[:MENTIONED_IN]->(Memory#123) {timestamp, context}
EVOLVED_FROM (Memory#456)-[:EVOLVED_FROM]->(Memory#123) {confidence, timestamp}
RELATED_TO (ALEX)-[:RELATED_TO]->(TurnPanel) {relationship_type}

Query Examples

Before (Current System)

// To find all projects user works on:
// 1. Fetch ALL memories
// 2. Run semantic search for "project"
// 3. Manually parse results for project names
// 4. No way to know if projects are related

const memories = await memoryStore.getAll();
const projectMemories = memories.filter(m => 
  m.text.includes('project') || m.text.includes('TurnPanel')
);
// Result: Incomplete, no relationship awareness

After (Graph-Enhanced)

// Single query returns all projects with full context
const projects = await graphQuery(`
    MATCH (u:User)-[:WORKS_ON]->(p:Project)
    RETURN p.name, p.status, p.repository
    ORDER BY p.status
`);

// Result: [
//   { name: 'TurnPanel', status: 'active', repository: 'KSubedi/turnpanel' },
//   { name: 'ALEX', status: 'active', repository: 'KSubedi/alex' },
//   { name: 'Law Nepal', status: 'planning', repository: 'KSubedi/law-nepal' }
// ]

// Multi-hop query: Find all tools used in active projects
const tools = await graphQuery(`
    MATCH (u:User)-[:WORKS_ON]->(p:Project)
    WHERE p.status = 'active'
    MATCH (p)-[:USES]->(t:Tool)
    RETURN DISTINCT t.name, t.category
`);

Measurable Outcomes

10-50x Faster relationship queries
30-50% Fewer tokens in memory injection
90-95% Recall accuracy (vs 75-85%)
<50ms Graph query latency

Risk Assessment

Risk Impact Mitigation
Graph database adds operational complexity Medium Use FalkorDB (Redis-based) for lightweight deployment; containerize with Docker
Migration may lose some historical context Low Keep original vector DB intact; run both systems in parallel during transition
Entity extraction accuracy below threshold Medium Implement confidence scoring; manual review for low-confidence extractions
Increased memory footprint Low Graph metadata is minimal (~5-10% of total memory size)

Technical Decisions Required

  1. Graph Database Selection: Neo4j (production-grade, full Cypher) vs FalkorDB (lightweight, Redis-compatible)
  2. Entity Extraction Method: Rule-based (regex + heuristics) vs LLM-based (more accurate but slower)
  3. Deployment Strategy: Local-only (user's machine) vs cloud-synced for multi-device support
  4. Query API: Direct Cypher exposure vs safe abstraction layer with predefined query templates
Next Steps: Upon approval, begin Phase 1 prototype with NetworkX to validate the approach before committing to production database selection.
