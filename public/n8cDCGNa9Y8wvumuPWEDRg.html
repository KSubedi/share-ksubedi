Graph Database Enhancement for TurnPanel Memory System

Author: Sheru (TurnPanel Agent) Date: August 7, 2026 Status: Proposal for Review

---

Executive Summary

TurnPanel's current memory system uses a two-tier architecture (core facts + episodic vector search) that works well for semantic recall but lacks relationship awareness and entity tracking. This proposal outlines integrating a graph database layer to enable:

  • 10-50x faster relationship-based queries
  • 90%+ precision in memory recall (vs. current 75-85%)
  • 30-50% reduction in token usage for memory injection
  • Multi-hop query capability (e.g., "What tools does the user use for AI projects?")
  • Temporal tracking of preference evolution

    • ---

    Current Architecture

    Two-Tier Memory System

    | Tier | Storage | Purpose | Limitations | |------|---------|---------|-------------| | Core | core.json (flat JSON) | Compact stable facts injected in every prompt | Max 24 entries, no relationships | | Episodic | vector-db/memories.json (HNSW) | Searchable facts/events with embeddings | No entity linking, no relationship tracking |

    Key Problems

    1. No relationship awareness: Cannot answer "What projects involve the user's AI work?" without scanning all memories 2. No entity resolution: "User prefers llama.cpp" and "User uses llama.cpp for local inference" are separate entries without explicit connection 3. No temporal graph: Cannot trace how a preference evolved over time 4. Multi-hop queries impossible: "Who does the user know that works at X?" requires N separate searches

    ---

    Proposed Solution: Hybrid Vector + Graph Architecture

    Architecture Overview

    `` ┌─────────────────────────────────────────────────────────┐ │ Query Layer │ │ (semantic search + graph traversal) │ ├─────────────────────────────────────────────────────────┤ │ Vector Index (current) │ Graph Index (new) │ │ - Fast similarity │ - Entity relationships │ │ - Broad recall │ - Multi-hop queries │ ├─────────────────────────────────────────────────────────┤ │ Memory Store (current) │ Knowledge Graph (new) │ │ - Text + embeddings │ - Nodes: entities/events │ │ │ - Edges: relationships │ └─────────────────────────────────────────────────────────┘ `

    Benefits

  • Non-invasive: Keep current vector search as primary, add graph as secondary
  • Hybrid retrieval: Fuse results from both systems for best recall + precision
  • No migration needed: Run parallel during transition

    Graph Schema Design

    Node Labels

    | Label | Description | Example | |-------|-------------|---------| | User | The person | User entity | | Preference | User preferences | "Prefers llama.cpp" | | Project | Ongoing work | "Law Nepal Project", "ALEX" | | Tool | Software/services used | "llama.cpp", "Composio" | | Conversation | Chat sessions | Conversation ID | | Memory | Episodic facts | Memory ID |

    Edge Types

    | Edge | Direction | Meaning | |------|-----------|---------| | [PREFERS] | User → Preference | User's stated preferences | | [WORKS_ON] | User → Project | Active projects | | [USES] | User → Tool | Tools the user uses | | [MENTIONED_IN] | Memory → Conversation | Where memory was mentioned | | [RELATED_TO] | Memory ↔ Memory | Semantic similarity | | [EVOLVED_FROM] | New Preference → Old Preference | Temporal evolution | | [BELONGS_TO] | Preference → Project | Contextual grouping |

    Implementation Options

    Backend Choices

    | Option | Pros | Cons | Effort | Recommendation | |--------|------|------|--------|----------------| | Neo4j (local) | Mature, Cypher query language, full graph features | Heavyweight, requires separate process | Medium | Overkill for now | | Memgraph | In-memory, PostgreSQL-compatible, real-time | Less mature ecosystem | Medium | Good alternative | | FalkorDB | Lightweight, Redis-like, good for AI agents | Smaller community | Low-Medium | Recommended | | NetworkX + SQLite | Pure Python, no external deps, full control | No native graph indexing | Low | For prototyping | | PuppyGraph | Zero-ETL, queries existing DB as graph | Requires setup | Medium | For production later |

    Recommendation: Start with NetworkX for rapid prototyping, migrate to FalkorDB for production (aligns with TurnPanel's local-first philosophy).

    Query Examples Enabled by Graph

    Current (Vector-Only)

    ` User: "What AI tools does the user use?" → System: Scan 5,000 memories, extract mentions via LLM (~2-3 seconds) → Result: 10-15 text snippets requiring synthesis `

    Graph-Enhanced

    `cypher MATCH (u:User)-[uses:USES]->(tool:Tool) WHERE tool.category CONTAINS 'AI' RETURN tool.name, tool.importance ORDER BY tool.importance DESC ` → Result: Direct structured list (~50ms)

    Multi-Hop Query

    `cypher MATCH (u:User)-[w:WORKS_ON]->(proj:Project)-[t:USES]->(tool:Tool) WHERE proj.name CONTAINS 'AI' RETURN DISTINCT tool.name, proj.name ` → Result: Tools used in AI projects (impossible with current system)

    Temporal Evolution

    `cypher MATCH (old:Preference)-[e:EVOLVED_FROM*]->(latest:Preference) WHERE latest.category = 'AI tools' RETURN old.text, latest.text, e.timestamp ` → Result: How preferences changed over time

    Input Memory

    "User prefers llama.cpp with an OpenAI-compatible API for serving local models on an Apple M5 Max Mac."

    Extracted Graph

    `json { "nodes": [ {"id": "user_001", "label": "User"}, {"id": "llama.cpp", "label": "Tool"}, {"id": "OpenAI-compatible API", "label": "Feature"}, {"id": "Apple M5 Max", "label": "Hardware"}, {"id": "local models", "label": "UseCase"} ], "edges": [ {"from": "user_001", "to": "llama.cpp", "type": "PREFERS"}, {"from": "llama.cpp", "to": "OpenAI-compatible API", "type": "PROVIDES"}, {"from": "llama.cpp", "to": "local models", "type": "USED_FOR"}, {"from": "user_001", "to": "Apple M5 Max", "type": "USES"} ] } `

    Query Example

    `cypher // "What tools does the user prefer for local models?" MATCH (u:User)-[prefers:PREFERS]->(tool:Tool)-[usedFor:USED_FOR]->(useCase:UseCase) WHERE useCase.name = 'local models' RETURN tool.name, prefers.confidence ``
